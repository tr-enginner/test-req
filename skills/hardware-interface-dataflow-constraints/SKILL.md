# 硬件接口与功能数据流方向约束

## 判定基准

- 始终把被测软件（CPU 侧软件）作为观察主体。
- 输入流是外部设备、单机或总线对端通过当前接口发送给被测软件的指令、数据、状态或事件：`外部对象 -> 当前接口 -> 被测软件`。
- 输出流是被测软件通过当前接口发送给外部设备、单机或总线对端的控制、请求、数据、状态、应答或遥测结果：`被测软件 -> 当前接口 -> 外部对象`。
- 不要按测试设备的收发方向、总线主从角色、请求/应答名称或源文档的叙述视角改变上述基准。
- 先识别被测软件、外部对象和实际承载数据的当前接口，再填写输入流、输出流及其表格。
- 方向证据不足时省略该流或使用调用方契约规定的空值；不要为了形成双向结构补造对称流。接口可以只有输入流，也可以只有输出流。

## 接口关联

- 每条流只能归属于直接承载它的接口，不得跨接口传递、复制或归因。
- 当软件从接口 X 接收信息，处理后再从接口 Y 发出信号时，把原始信息仅记为接口 X 的输入流，把软件实际发出的信号仅记为接口 Y 的输出流。
- 在功能需求中把跨接口转换写入 `processing`，但不要把接口 X 的输入复制为接口 Y 的输入，也不要把接口 Y 的输出反写为接口 X 的输出。
- 如果硬件接口报告中的方向与本 Skill 冲突，依据原始需求证据和被测软件边界重新判定，不得照抄错误方向。

## 表格归类

- 把表格放到它直接描述的数据流一侧。接收帧、外部指令或外部采集数据表属于输入侧；软件发送帧、控制信号、请求或遥测数据表属于输出侧。
- 不要仅因表格位于某段文字之后、与相邻表属于同组或源文档使用“发送/接收”等无主体词语，就继承方向。
- 无法确认表格所描述的主体和方向时不要猜测归类。

## 示例与反例

- 软件通过 CAN 接收“开启指示灯”指令：该指令是 CAN 接口输入流。
- 软件通过 CAN 返回指令应答包：该应答包是 CAN 接口输出流。
- 软件处理上述指令后通过 GPIO 或 FPGA 接口向指示灯单机发送高电平控制信号：该信号是 GPIO 或 FPGA 接口输出流；如果指示灯无返回，该接口输入流为空。
- 禁止把“开启指示灯”指令同时写成 GPIO 或 FPGA 接口输入流。它没有通过该下游接口进入软件。
- 软件向外设发送读取请求、外设返回数据：读取请求是输出流，返回数据是输入流；主从角色不改变方向。

## 输出前自查

逐项确认：

1. 输入流的箭头终点是否为被测软件。
2. 输出流的箭头起点是否为被测软件。
3. 每条流是否确实穿过当前接口。
4. 是否错误复制了其他接口上的上游指令或下游信号。
5. 单向交互是否保持一侧为空，而非补造不存在的数据流。
6. 每张表是否与所在一侧的数据流方向一致。
