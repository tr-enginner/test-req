# 硬件看门狗接口领域补充

同时使用 `$hardware-interface-modeling` 和 `$hardware-interface-dataflow-constraints`。本 Skill 只补充看门狗领域经验；发生冲突时，以这两个通用 Skill 为准。

## 检索线索

- 从当前候选来源开始，检查主 SRS 的运行环境、硬件环境和相关功能章节，并全文检索“复位”“看门狗”“硬件狗”“喂狗”“狗咬”“Watchdog”。
- 补充文档只能补充已由主 SRS 立项的看门狗接口，不能单独新增候选。
- 汇总直接支持看门狗芯片、喂狗方式、超时时间和超时后结果的最具体来源章节，不因“复位”一词单独出现而扩大候选边界。

## Overview 内容组织

- 看门狗 `overview`（测试需求界面中的 summary）必须包含芯片型号、喂狗端口、喂狗电平或动作、狗咬时间，以及狗咬后的结果。
- 当前项目来源缺失任一必备要素时，在对应位置写 `XX`，不得省略，也不得根据示例、芯片资料、协议常识或其他项目猜测具体值。
- 狗咬后的复位对象或其他结果只写来源明确的事实；结果不明确时写 `XX`。
- 删除器件原理背景和重复描述，不把初始化寄存器值、默认配置或无证据的故障处理过程写入 `overview`。

### Summary 参考模板

- 看门狗 `overview` 应参考下述模板的内容结构和详细程度。
- 项目实际值必须来自当前候选及其来源文档；示例中的 MAX706、P1.7、0、1 电平跳变、1.6s 和计算机复位不得作为所有项目的固定事实。

```
硬件狗芯片为MAX706，通过向P1.7端口0、1电平跳变实现喂狗，狗咬时间为1.6s，狗咬后计算机复位
```

## 数据流与表格

- 始终以被测 CPU 软件为主体判定输入输出。软件驱动端口或信号完成喂狗时，可生成“输出流：喂狗信号。……”；没有其他真实数据流时，输入流保持空字符串。
- 狗咬后的复位结果属于接口行为，写入 `overview`；不得仅因复位结果凭空创建输入流或四级 `topics[]`。
- 只有来源确实存在独立看门狗事务时才生成 `topics[]`，不得为模板中的一句总述机械创建四级标题。
- 端口、时序或静态映射原表按通用规则完整引用到 `overview_tables`；不得新造、截断、删改、重画或摘要化原表。

## 通用契约边界

- 使用统一 `interface_id`、三级标题、可选 `topics[]` 及通用输入输出字段。
- `topics[]` 禁止 `content`，所有说明性正文统一进入 `overview`。
- 不新增字段，不恢复看门狗专属 block 或类型专属 DOCX 布局。
- 不得覆盖通用 Skill 的来源边界、CPU 方向、表格唯一归属和跨接口隔离规则。
