# 接口测试需求生成
## source_refs契约
每行`source_refs`必须是非空、去重数组，逐字复制原始source bundle的`sections[].source_ref`并至少包含一个`primary::`；supporting只能补充。合法：`["primary::SRS-3.2.1", "supporting-002-protocol::SRS-8.4"]`。禁止裸章节ID、标题、DOCX路径、source plan信息和table_id。硬件接口派生文本只能帮助组织内容，不能作为`source_refs`；只引用直接支持当前接口测试需求的最具体原始章节。

## 输入职责

- 从 `hardware_interface_report_text_path` 确认接口名称、接口标识、通信对象、方向、消息或信号、输入输出流、格式字段及承载数据帧格式的第三章明确表号。
- 从 `source_artifacts_path` 引用的 document structure 确认触发条件、功能动作、状态更新、计数规则和应答处理；正文读取 `sections[].text`，表格读取 `tables[].table_html`。
- 只把 `target_interface_batch` 用作当前批次范围和检索提示，不把提示本身当作证据。
- 所有事实必须能在两份输入之一定位；完整通信需求优先同时保留两类证据。

## 工作流

1. 读取目标接口标识、接口名称及其在第3.1章下的全部通信主题和检索词；一个接口标识不得拆给多个worker。
2. 在硬件接口文本中定位接口契约和数据流上下文。
3. 在功能源文本中检索同名消息、指令、字段、计数器和处理动作。
4. 对同一接口事务成对提取正常和异常证据。请求—应答类只组合“请求名称和表号 + 正常应答名称和表号 + 明确错误字段/异常类型 + 错误应答、不应答或丢弃”；不组合接收后的解析暂存、计算、业务执行、模式切换、内部状态、存储、错误计数或日志。正常和异常证据均存在时合并在同一row。
5. 按 [需求范围分类](references/scope-classification.md) 在合并前判断主要验证对象，将候选项分为 `interface`、`functional`、`performance`、`safety_reliability` 或 `mixed`；功能、性能和安全性/可靠性项不得生成row，混合项仅在剥离其他测试类型后仍存在未被覆盖的独立接口契约时生成row。
6. 按 [需求模式](references/requirement-patterns.md) 识别候选项。
7. 按 [关联与拆分规则](references/association-and-splitting.md) 先组合请求—响应闭环和同类处理变体，再拆分确有独立触发、处理结果或异常后果的行为；输出前执行语义最小化。
8. 按 [外部接口覆盖与系统特性规则](references/external-interface-coverage.md) 检查每个外部输入输出方向的内容、协议时序和接口数据异常处理，并排除通信设施故障管理。
9. 当目标接口由原文确认属于 CAN 时，必须读取 [CAN 接口测试覆盖规则](references/can-interface-coverage.md)，按总线实例、输入流、单帧字段、多帧异常、事务隔离和有证据的高优先级广播执行覆盖检查；非 CAN 接口不得套用该规则。
10. 按 [标识与表格规则](references/id-and-table-rules.md) 直接生成表4.3-1的五个业务字段，保留来源测试需求标识，并用 `AUTO_TR_JK` 标记需要统一编号的接口项；序号由最终DOCX渲染器生成。
11. 按 [质量检查表](references/quality-checklist.md) 自检；证据不足、覆盖缺口或冲突时写入 `open_questions`。

## 正式候选项成立条件

- 接口、消息/指令/数据/信号以及软件行为明确。
- 至少存在一个可测试的正常行为或异常行为；只有一侧证据时必须如实缩小`related_description`范围，并把另一侧覆盖缺口写入`open_questions`。
- 外部接口应分别检查输入和输出方向，并覆盖原文明示的正常、异常、内容正确性和时间/时序要求。
- 接口名称能够映射到硬件接口文本中的接口实例。
- 简单 GPIO、秒脉冲、FPGA 状态等信号接口无需具有帧长度或校验和。
- 只有硬件背景而没有软件交互，或只有格式而没有软件使用场景时，不生成正式候选项。
- 覆盖准则用于发现缺口，不构成事实证据；原文没有时间阈值、异常类型或系统特性指标时只写 `open_questions`。
- 需求的主要验证对象必须是跨接口传递的数据、信号或事务契约；纯性能指标，以及总线/控制器故障检测、隔离、重新初始化、冗余重构和自动恢复能力，不成立为4.3候选项。
- 有效数据接收后的计算、业务判断、内部状态管理、数据处理或存储属于功能需求；没有明确输出接口、接收方和输出格式的“转发”也属于功能需求。
- 接收后的动作只有形成明确对外应答契约时才能成为4.3内容；正确业务功能本身由4.1覆盖。“不执行正常业务动作”只可收紧为“不产生正常接口应答”，不得展开被禁止的内部业务动作。

## 数据帧格式引用

- 第三章硬件接口表格是数据帧格式的唯一展示位置。4.3中的“格式测试”通过正确请求的正常应答和错误请求的错误应答、不应答或丢弃来验证，不是在TR中重新定义格式或描述内部解析。
- 能定位格式表时使用明确表号，例如“收到符合表3.x规定格式的请求时，按照表3.y返回应答”。请求与响应对应不同表格时分别引用两个真实表号。
- 不复制Byte/W字节位置、逐字节布局、固定值、取值范围、位域、字段编码、数据区完整定义、字段含义、完整帧结构，以及表格已承载的帧长度或字段清单。
- ID、LENGTH、SUM等字段名只有在直接参与合法性校验、异常条件或差异分支时才能保留；不写它们的字节位置、固定值或完整定义。
- 找不到表号时不得编造，也不得用复制格式正文代替；保留证据充分的接口行为，并在`open_questions`写明接口、消息、缺失表号和已搜索关键词。

## 同类处理族合并

- 合并范围限定在同一`interface_id`。先按通信方向和双方、正常应答、错误字段集合及错误应答建立合并签名，再生成rows；内部业务处理、错误计数、日志和状态差异不参与签名。
- 类型和处理签名相同的消息或指令必须合并。快帧/慢帧、速变/缓变等名称或业务分类，以及ID、地址、长度、索引、数据块数量、载荷布局、格式表号、更新/采集/发送周期或独立触发不同，不是拆分理由。
- 周期差异转交性能测试，不写入4.3。快帧遥测和慢帧遥测等单向输出只生成一行，列出消息名称、接收方及各自第三章格式表号，不补造应答或接收后的处理。
- 只有通信方向或双方不同且不构成同一事务、正常应答不同、错误字段集合不同、错误应答不同或请求—响应语义不同时才拆分。
- 合并项的`source_refs`按首次出现顺序合并去重。多个显式来源TR号按首次出现顺序以`、`连接；全部为派生接口项时只写一个`AUTO_TR_JK`。`related_description`合并共同范围和校验字段名并去重。

## 输出约束

- 只输出当前批次的 raw JSON；其中 `rows` 必须直接匹配表4.3-1，不输出发送方、接收方、格式字段、正常/异常行为等分析过程对象。
- 每个 row 必须且只能包含 `interface_requirement_description`、`test_requirement_id`、`source_refs`、`related_description`、`interface_name`、`interface_id` 六个字段，不输出 `sequence`；`source_refs`必须回到原始source bundle且至少包含一个primary引用。
- raw 顶层必须且只能包含 `batch_id`、`interface_name`、`interface_id`、`rows`、`open_questions`，不输出任何哈希字段、`skill_version` 或 `prompt_version`；缓存一致性元数据只由工作流计划管理。
- 保留原文中已存在的 `TR-GN-*`、`TR-XN-*` 等测试需求标识。
- 对纯接口格式、数据异常处理或事务交互派生项写入 `test_requirement_id: "AUTO_TR_JK"`，但不分配全局 `TR-JK-NNN`。
- 请求—应答类 `interface_requirement_description` 使用紧凑结构：`收到符合表3.x规定格式的<请求>时，按照表3.y返回<正常应答>；收到<ID、DLC、长度、序号、SUM/CRC等原文明示错误>时，执行原文明示的<错误应答、不应答或丢弃>。`
- 正确情况只保留请求名称、请求表号、应答名称、应答表号和可观察应答结果；错误情况逐项列出原文明示的错误字段或异常类型及对应外部响应。
- 单向广播、遥测上报等无应答输出继续保留，但只写发送消息名称、接收方及第三章格式表号，不补造应答、周期或对端接收后的处理。
- 不写入接收后的解析暂存、计算、业务判断、指令执行、模式切换、内部状态、存储、内部错误计数或日志；只有原文明确编码进对外应答的内容才可保留。
- 明确列出直接参与校验的异常字段，不用“等”“相关字段”“异常情况”等省略表达；普通载荷字段和完整布局由被引用表格承载。
- `interface_requirement_description` 与 `related_description` 必须一致：正文同时描述正常和异常时才可写“接口正常/异常”；正文只有正常行为时只写“接口正常情况的测试”；正文只有异常行为时只写“接口异常（明确字段）情况的测试”。
- 来源同时给出正确和错误应答时，正文必须同时写正常应答和错误字段对应的错误应答、不应答或丢弃，不复述正确请求被接收后的内部处理。
- 来源未明确异常条件或响应时保留正常需求，不推导异常行为，并在`open_questions`写明具体接口、消息及缺失的异常条件或异常响应。
- 无法确认的信息写入顶层 `open_questions`，不得生成不完整表格行或猜测。

## 禁止事项

- 不读取 DOCX 二进制、源代码、`software-analysis.json`、`req-segments*` 或 `req-document-structure.json`。
- 不使用通用协议知识补写原文没有的字段、阈值、发送方、接收方或容错行为。
- 不处理 payload 之外的接口主题。
- 不生成最终 JSON、全局编号或 DOCX。
- 不得仅在`related_description`写“正常/异常”，而让`interface_requirement_description`只包含正确情况。
- 不得把第三章表格中的数据帧格式复制到4.3接口需求描述中。
- 不得先按消息名称生成多个处理方式相同的row，再依赖finalize做文本去重。
