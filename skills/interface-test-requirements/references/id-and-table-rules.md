# 标识与表格规则

## 测试需求标识

- 保留原文已有的 `TR-GN-*`、`TR-XN-*` 或其他测试需求标识。
- 一个接口候选项可以关联多个来源标识。
- 同类处理族合并后，多个显式来源标识按原文首次出现顺序去重，并在现有`test_requirement_id`字符串中使用`、`连接；不得只保留第一个标识。
- 纯接口格式、接口数据异常处理或事务交互派生项没有来源标识时，写入 `test_requirement_id: "AUTO_TR_JK"`；故障检测、隔离、复位、重构或恢复项不得申请该标识。
- Worker 不分配 `TR-JK-NNN`；最终合并工具按稳定排序把 `AUTO_TR_JK` 替换为正式编号。

## 相关说明

最终工具根据内容组合以下说明：

- 接口信息格式及内容的测试；
- 接口正常情况的测试；
- 接口异常（逐项字段）情况的测试；
- 接口正常和异常情况的测试。

## 4.3 表格

raw JSON 的 `rows` 保存DOCX固定六列表格中的五个业务字段，不保留序号或额外分析字段：

- `interface_requirement_description`：接口需求描述；
- `test_requirement_id`：对应测试需求标识；
- `related_description`：相关说明；
- `interface_name`：对应接口名称；
- `interface_id`：接口标识。

raw中只保存上述五个业务字段，不保存序号。DOCX表格仍为六列，渲染时按最终稳定排序使用行下标生成“序号”列。

`interface_name`只保留规范化接口名称：去掉开头的章节编号，并去掉末尾的“及相关数据流”。例如“3.1.1 CAN总线接口及相关数据流”输出为“CAN总线接口”。

`interface_requirement_description` 必须把通信双方、方向、触发、第三章格式表号、格式校验行为、接口接收/应答、明确的跨接口输出和接口数据异常处理整合为可直接交付的需求句。数据帧格式由硬件接口表格唯一展示，不得复制Byte/W布局、固定值、位域、编码、字段含义或完整帧结构；后续业务处理和内部存储不得写入。

找不到真实表号时不得编造或复制格式作为替代；在`open_questions`记录接口、消息、缺失表号和已搜索关键词。字段名仅在直接参与校验、异常条件或分支差异时保留。

4.3.2 固定为：充分性 `C1、C2`，终止要求 `Z1、Z2`，所有需求项为高优先级。
