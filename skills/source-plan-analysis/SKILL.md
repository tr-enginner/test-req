# 来源规划分析

## 概述

用这个 skill 来分析 Phase 2 的文档来源规划问题，也就是如何从候选文档里选出：
- 唯一主文档 `primary_srs_path`
- 补充文档 `supporting_documents`
- 忽略文档 `ignored_document_paths`

它适合处理这类任务：
- 从候选文档清单中挑出唯一需求规格说明书
- 给补充文档标注 `protocol`、`interface_protocol`、`data_definition`、`other_support`
- 判断某份文档该算主骨架、补充来源还是直接忽略
- 多份疑似 SRS 并存时，判断是否应停止并报错
- 复核 `source-plan.json` 结果是否合理

不要用这个 skill 替代 workflow 的 artifact 管理与 schema 校验。它只负责“怎么选来源”的方法。

## 规划方法

### 1. 先选唯一主文档

主文档必须是唯一的需求规格说明书，并且承担章节骨架来源的角色。

优先考虑这些信号：
- 文档标题、封面、目录中明确出现“需求规格说明书”
- 文档整体覆盖系统/软件需求主体，而不是某个局部接口或附录
- 目录结构完整，能作为后续章节骨架
- 文档不是仅包含协议、接口定义、数据字典、会议纪要、封面或引用资料

如果存在多份都很像 SRS 的强候选：
- 不要猜
- 直接判定为歧义并停止，让流程报错

### 2. 再识别补充文档

主文档确定后，再从剩余文档里找补充来源。

补充文档常见角色如下：
- `protocol`
  以通信协议、交互流程、遥测遥控格式为主
- `interface_protocol`
  以接口说明、总线交互、接口章节、接口表格为主
- `data_definition`
  以数据项、字段、参数、数据块定义为主
- `other_support`
  其他仍然有需求支撑价值，但不属于以上三类

只有对后续需求抽取、章节补充有帮助的文档，才进入 `supporting_documents`。

### 3. 决定哪些文档应忽略

以下文档通常应放入 `ignored_document_paths`：
- 封面、首页、审批页
- 纯元数据文档
- 参考资料目录
- 会议纪要
- 任务分工、计划说明
- 与需求链路明显无关的说明文档

如果一份文档没有需求承载作用，只是上下文噪声，也应忽略。

### 4. 处理候选冲突

遇到这些情况时，优先停止而不是猜测：
- 无法唯一确定主 SRS
- 多份文档都像主 SRS，且证据强度接近
- 候选文档本身抽取失败，无法形成可靠判断

遇到这些情况时，可以继续但要做保守判断：
- 补充文档角色有轻微交叉
- 文档同时兼具协议和数据定义特征

这类情况可以按“主要用途”选择一个最贴近的 supporting role。

## 判定优先级

做规划时遵循以下优先级：

1. 先保证主 SRS 唯一且可靠
2. 再识别对后续章节补充真正有价值的文档
3. 最后把其余噪声文档放入 ignored

不要为了“全收进去”而降低主文档判定标准。

## 输出约束

输出结果必须始终对齐 `source-plan.json` 的标准结构：
- `primary_srs_path`
- `supporting_documents`
- `ignored_document_paths`

其中：
- `primary_srs_path` 只能有一个
- `supporting_documents` 中每项只包含 `path` 和 `role`
- 同一路径不能同时出现在多个列表中
- 有抽取错误的候选文档不要选入主文档或补充文档

## 约束

不要：
- 在多个强 SRS 候选中凭感觉二选一
- 把协议文档当主骨架文档
- 把明显无关文档塞进支持列表
- 因为文件名像需求文档就忽略正文与目录证据
- 把同一文档同时放进主文档和补充文档
