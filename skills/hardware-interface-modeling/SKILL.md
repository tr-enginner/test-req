# 硬件接口通用建模

把任务候选中的真实接口作为“XX接口”，严格按以下顺序建模。一次只处理一个 `candidate_id`，并同时使用 `$hardware-interface-dataflow-constraints`。

## 条件加载领域 Skill

- 始终使用本 Skill 和 `$hardware-interface-dataflow-constraints`。
- `interface_kind=can` 时额外加载 `$can-bus-interface-analysis`；`interface_kind=ad` 时额外加载 `$ad-acquisition-interface-analysis`；`interface_kind=serial` 时额外加载 `$serial-interface-analysis`；`interface_kind=mil1553b` 时额外加载 `$mil1553b-interface-analysis`；`interface_kind=watchdog` 时额外加载 `$watchdog-interface-analysis`。
- 归一化类别优先。只有 `interface_kind=other` 时，才使用接口名和候选 `keywords` 兜底：明确包含“CAN”“CANA”“CANB”或“CAN总线”时加载 CAN Skill；明确包含“AD采集”“A/D采集”“模数采集”时加载 AD Skill；明确包含“串口”“UART”“RS232”“RS422”“RS485”时加载串口 Skill；明确包含“1553B”“MIL-STD-1553B”，或明确说明 GJB 289A 与 1553B 等效、符合、兼容或对应时加载1553B Skill；明确包含“看门狗”“硬件狗”或“Watchdog”时加载看门狗 Skill。孤立的“1553”或GJB 289A不得触发。
- `other` 候选同时命中多个专用领域时停止建模并报告分类冲突，不得同时加载多个专用 Skill。
- 专用 Skill 只补充检索词和领域组织经验。若它与本 Skill 或数据流约束冲突，以本 Skill 和 `$hardware-interface-dataflow-constraints` 为准；不得因此改变通用 raw schema、标题层级、表格归类或渲染结构。

## XX接口成立条件与检索方法

- 先用 `interface_name`、`interface_kind` 和全部 `keywords` 检索主 SRS，再组合通信对象、指令、帧、信号、采集对象、地址、应答、协议等上下文词扩展检索。
- 优先检查 SRS 的硬件接口章节，同时检查硬件环境、运行环境及相关功能章节；再检查补充文档的协议附录、接口协议、数据约定、数据定义和数据协议章节。
- 只有源文档明确体现项目软件经当前接口与外部对象发生真实数据交互时才成立。
- 看门狗是窄范围例外：主 SRS 出现看门狗对象及相关说明即可成立；建模时从运行环境、硬件环境、相关功能章节及全文中的“复位、看门狗、硬件狗、喂狗、狗咬、Watchdog”补充证据。
- 补充文档只能补充主 SRS 已立项接口的细节，不能新增接口边界。
- 只有硬件清单、器件说明、板卡说明、架构背景、初始化配置、复位、引脚配置或泛化接口名称时不成立，输出 `{"interface": null}`。
- 上述不成立规则不用于否定已经按看门狗窄范围例外立项的候选。

## XX接口总述

- 只写有证据且必要的接口参数事实和接口关系：接口数量、通信对象、接口/总线类型、基地址、时钟、波特率、工作模式、位数、量程、转换时间等。
- 不写上电、复位或初始化时机、初始化动作、寄存器初值、默认配置和初始化结果；这些内容属于4.1初始化功能。
- 默认不写中断号、优先级、触发电平/边沿、ISR、中断使能和中断挂接关系。窄范围例外：CAN和1553B候选可在源文档明确给出时，将中断号或名称及挂接关系写入 `overview`；仍禁止写优先级、触发方式、ISR、中断使能和寄存器配置。当前候选本身是独立中断或离散信号接口时，真实穿过接口的事件仍可作为数据流，但不能借此把配置说明写入overview。
- 除上述 CAN 和1553B中断挂接例外外，删除的初始化和中断配置内容不得转移到四级topic、input_flow或output_flow。
- 不扩展协议原理、器件背景或无证据的通用知识。
- 看门狗候选按 `$watchdog-interface-analysis` 组织 `overview`：必须包含芯片型号、喂狗端口、喂狗电平或动作、狗咬时间和狗咬后的结果，缺失项写 `XX`。
- 数据采集过程、收发时序、地址说明及其他有证据的非数据流说明也统一写入三级节点 `overview`，不要分散到四级主题字段。
- 允许在总述后引用直接说明当前接口地址或静态映射关系的原表，包括总线地址表、接口地址表、寄存器地址表、端口映射表和通道地址表、数据收发过程（如果需求中明确写了），数据收发过程在总述中另起一行描述。
- 这些表写入 `overview_tables`，在最终文档中位于总述之后、第一个四级标题之前；没有时写空数组。
- 初始化设置表、初始设置表、复位配置表、寄存器初值表以及中断设置表、中断配置表、中断分配表、优先级或触发方式表不得写入`overview_tables`。
- 主要描述地址、端口、通道或静态接口关系、仅包含少量中断引脚或中断信号行的混合原表允许完整保留；不得裁剪其行列。表格主用途无法确认时不引用。
- 事务帧、指令、采集数据或应答格式表不得放入 `overview_tables`。

### 间接指令与数字量采集

- 当前接口包含“间接指令”时，`overview` 只聚焦来源明确的指令码、输出地址和脉冲参数（脉宽、电平）；删除电路构成、器件连接原理及与这些核心要素无关的背景说明。
- 间接指令原表只按通用规则在最匹配的一个位置完整引用一次。内容等价或同一 `table_id` 的指令表不得在 `overview_tables`、接口顶层流和四级 `topics[]` 间重复；不同事务且内容不等价的原表仍分别保留，不得因去重而遗漏真实定义。
- 当前接口包含“数字量采集”时，优先检索并完整引用能够呈现采集地址和参数名称的真实原表；该类静态地址/参数映射表放入 `overview_tables`。不得从正文重画表格，也不得裁剪原表中已有的其他列。
- 数字量采集的正文不再逐项重复表格已经给出的地址。数据流只明确实际采集参数及其定义，不重复“软件通过接口读取”“按地址采集”“接口输入软件”等接口动作。

## 三级标题生成

- 每个候选接口独立生成一个三级标题，同类的不同候选不得在建模阶段合并。候选发现阶段已经合并的同父章节 CANA/CANB 是一个候选，必须生成一个三级标题并同时读取其全部来源，不得重新拆成两个接口章节。
- 贴着 `interface_name` 轻度规范化为“XX及相关数据流”。接口名已有“接口”或“总线”时直接追加“及相关数据流”，不得重复写“接口接口”或“总线接口”。
- 不脱离原文重命名接口，不按 `interface_kind` 替换真实接口名。
- 同时生成独立的展示标识 `interface_id`，不得把内部 `candidate_id` 当作文档标识。格式必须为 `IF-<英文标识>-<三位序号>`；英文标识只能包含大写 ASCII 字母、数字和必要的连字符，不得包含中文、小写字母，也不得把真实接口名中的“接口”“输出”等中文包装词直接拼入标识。
- 英文标识优先使用协议、总线、器件功能或通道的通用英文缩写：一级 CAN 使用 `IF-CAN0-001`，二级 CAN 使用 `IF-CAN1-001`，AD 使用 `IF-AD-001`，DA 使用 `IF-DA-001`，UART 使用 `IF-UART-001`，RS422 使用 `IF-RS422-001`，SPI 使用 `IF-SPI-001`，SpaceWire 使用 `IF-SPACEWIRE-001`，1553B 使用 `IF-1553B-001`。同类同通道接口使用末尾三位序号区分，例如 `IF-AD-001`、`IF-AD-002`；禁止生成 `IF-DA输出-001` 这类中英文混合标识。

## 四级标题判定

- 优先寻找同一父标题下的一组并列通信事务、请求-响应对、信号主题、采集主题或数据块主题；通常一簇并列子标题就是完整候选集合。
- 父标题只用于定位，不是合并依据。并列子标题分别表达独立数据流时必须分别生成四级小节。
- 四级标题优先采用直接表达通信主题的原题，例如轮询、间接指令、上行数据块、广播数据或具体采集对象。
- 网络结构、技术指标、标识符、地址、类型、格式说明等支撑性标题不能直接成为四级标题。
- 来自功能需求或处理章节的标题不能直接照搬；只有它明确表达当前接口的数据交互主题时才能作为证据。
- 去掉“格式说明”“应答格式说明”“传送格式”等包装尾词；父标题已表达的共性语义可从子标题中去重；最终统一为“xxx及相关数据流”。
- 例如“速变遥测轮询及应答格式说明”规范为“速变遥测轮询及相关数据流”。并列的速变遥测、缓变遥测和固存工作表遥测不得合成一个“轮询控制序列及相关数据流”。
- 原文没有独立四级主题时，允许把具体输入输出放在三级节点。存在明确但无可直接采用标题的数据流时，从原文明示的指令、信号、采集对象或事务名称轻度归纳，禁止使用“接口数据流”“相关信息”等泛称。

## 四级内容生成

- 四级标题确定后，先锁定该主题来源章节中的全部事务相关原表，再整理输入流和输出流。
- 已锁定的事务表必须全部归入该小节的输入侧或输出侧，不得因正文已概括、表格较多或只需部分字段而省略。
- 来源章节没有表格但明确存在数据流时仍可生成小节，只写有证据的流，不编造格式细节。
- 一个请求、返回和应答构成同一通信事务时放在同一四级小节，不按方向拆成不同标题。
- `topics[]` 不设置 `content` 字段，只保留标题、来源、输入输出流和相应原表；说明性正文全部放入三级节点 `overview`。

## 输入流与输出流生成

- 输入流固定写成“输入流：<短主题>。<简短说明>”，输出流采用相同结构。
- 冒号后只放简短的数据、指令、信号、应答或采集对象名称，不写成长句。
- 简短说明用一两句介绍谁通过什么总线/接口接收或发送了什么内容；如果对应表格能直接支撑这段描述，就自然接出“格式如下表所示”之类的引导语。
- CAN 候选按 `$can-bus-interface-analysis` 的窄范围例外处理：数据流只写数据内容短名和内容说明，不重复“通过 CAN 总线”“经 CAN 接口”或通信对象等已由 `overview` 说明的通信方式。
- 看门狗候选按 `$watchdog-interface-analysis` 处理：喂狗信号可作为输出流，狗咬后的复位结果只写入 `overview`，不得凭空创建输入流或四级标题。
- 数字量采集流只写参数名称或短名及参数定义；采集地址由对应原表承载，流文本不得复述地址或接口动作。
- 只有输入或只有输出时只填写存在的一侧，另一侧写空字符串并保留空表格数组，不补造对称流。
- 始终以被测 CPU 软件为主体，并禁止把上游接口指令复制为下游接口输入或反向归因。
- 1553B候选且软件明确作为RT时，描述当前RT的子地址表按 `T/R=0` 输入、`T/R=1` 输出解释；非RT、主体不明或与直接交互证据冲突时，仍按被测CPU软件边界判定，无法消歧则不猜测归类。

## 表格使用与归类

- 只引用 source artifacts 中真实存在的 `table_id`；不新造、截断、删改、重画或摘要化原表。
- 接口级地址、寄存器和静态映射表可放入 `overview_tables`，但初始化及中断配置类原表必须排除，混合表按主用途判定。
- 接收帧、外部指令和外部采集数据格式表放入对应 `input_tables`；软件发送帧、控制信号、请求、应答或遥测数据格式表放入对应 `output_tables`。
- 同一 `table_id` 在一个接口内只能出现一次，不能同时放入总述、顶层流或任一四级主题。
- 无法直接判断方向时先依据表格内容；仍不明确且与相邻已归类表同主题、同章节并连续解释同一组数据时，才继承相邻表方向。
- 无法唯一确认 `table_id` 或归属时不要猜测。

## 输出前自查

1. 接口是否有主 SRS 中的真实软件交互证据。
2. 三级标题是否保留真实接口名，四级标题是否逐项表达独立通信主题。
3. 总述是否仅含必要接口事实且没有初始化配置或禁止的中断配置说明；1553B中断挂接例外是否仅包含有证据的中断号或名称及挂接关系；`overview_tables`是否排除了初始化设置表和中断设置/配置/分配表，同时保留了以地址/端口/通道映射为主的混合原表。
4. 是否先锁定主题原表，再归类输入输出，且没有遗漏或重复 `table_id`。
5. 输入输出是否使用固定短主题格式，并以被测软件为方向基准。
6. 每个 `source_ref` 和 `table_id` 是否逐字存在于已读取 source artifacts。
7. `interface_id` 是否符合 `IF-<全大写英文标识>-<三位序号>`，只包含大写 ASCII 字母、数字和必要连字符，不含中文或小写字母，区别于 `candidate_id`，并与真实接口名称相符；是否避免了 `IF-DA输出-001` 这类错误；`topics[]` 是否完全没有 `content` 字段。
