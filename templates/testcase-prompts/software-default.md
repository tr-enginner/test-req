# 软件项目通用提示词模板

## 适用范围
- 模板 Key：`TR-DG-STEP-GENERATED`
- 说明：适用于 software / software_variant 的默认回退模板。

## 业务说明
当软件项目未命中更具体测试类型模板时使用。 提示词正文已收敛为短结构，业务人员如需优化，优先调整“类型专属规则”和“输入信息”的表达，不要在 `prompt` 代码块中加入大段示例或教学说明。

## 占位符
- `{tr_id}`：测试需求标识。
- `{tr_handling}`：测试需求的处理/功能描述。
- `{tr_name}`：测试项名称；仅在正文中出现时需要保留。
- `{tr_sufficiency}`：充分性要求。
- `{tr_testMethod}`：测试方法。
- `{tr_passCriteria}`：通过准则。
- `{tr_input_flow}`：输入流说明。
- `{tr_output_flow}`：输出流说明。
- 若正文中未使用某个占位符，可忽略对应说明。

## 提示词正文
```prompt
### 任务目标
你要为一条软件测试需求生成确认测试用例。

### 输出格式
- 只输出 JSON 数组。
- 每个用例包含 `test_case_name`、`test_purpose`、`test_step`。
- `test_step` 是数组；每个元素只包含 `步骤描述` 和 `预期结果`。

### 通用生成规则
- 只输出严格 JSON 数组，不要输出解释、标题或代码块标记。
- 仅围绕当前 requirement 生成，不补充无关场景。
- `步骤描述`写人工操作，`预期结果`写可观察、可验证结果。
- `步骤描述`和`预期结果`都以中文句号结尾。
- JSON 必须使用双引号、无末尾逗号、可直接解析。

### 类型专属规则
- 优先依据测试方法、通过准则和充分性要求组织步骤。
- 如果当前 requirement 可以在一个主用例内完成验证，不要无故拆成多个用例。
- 预期结果必须覆盖需求、章节背景和输出流中明确给出的可观察输出，不要只写“软件正确处理”这类笼统结果。
- 若步骤最终需要使用关键字 Documentation 格式，最终步骤中不得保留未解析的占位符；尤其是 `${time}` 必须给出具体值。

### 输入信息
- 测试项名称：{tr_name}
- 测试需求：{tr_id}：{tr_handling}
- 充分性要求：{tr_sufficiency}
- 测试方法：{tr_testMethod}
- 通过准则：{tr_passCriteria}
```
