# 测试版功能测试提示词模板

## 适用范围
- 模板 Key：`test-功能测试-STEP-GENERATED`
- 说明：适用于 software / software_variant + 功能测试。

## 业务说明
用于软件功能点验证场景。提示词正文已收敛为短结构，业务人员如需优化，优先调整"类型专属规则"和"输入信息"的表达，不要在 `prompt` 代码块中加入大段示例或教学说明。

## 占位符
- `{title}`：测试需求项名称。
- `{requirementContext}`：测试需求项简介。
- `{inputFlowContext}`：输入流说明。
- `{processingContext}`：测试需求项具体涉及的处理逻辑。
- `{outputFlowContext}`：输出流说明。
- `{constraintContext}`：测试要求。
- 若正文中未使用某个占位符，可忽略对应说明。

## 提示词正文
```prompt
### 任务目标
你要为一条功能测试需求项生成测试用例。输入的"处理"字段中包含多个"TR-ID：TR-描述"条目，你需要理解每个TR描述中的逻辑子部分，并根据测试需要合理组合，生成覆盖所有逻辑子部分的测试用例。

### 输出格式
- 只输出 JSON 数组。
- 每个用例必须包含 `test_case_name`、`test_purpose`、`covered_tr_items`、`test_step`。
- `test_case_name` 使用简洁的中文短语描述该用例的测试场景，如"上电标识为上电运行时的默认引导参数设置"，不要使用"TC_BOOT_001"等编号作为名称。
- `covered_tr_items` 是一个 JSON 字符串数组，列出本用例选取了依据的所有 TR-ID，如 ["TR-GN-BOOT-001", "TR-GN-BOOT-003"]。
- `correspond_fun_id` 是一个字符串，从 `<normalization_context>` 中的 `requirement_id` 原样照抄（、分隔的多ID格式）。示例：若当前需求的 `requirement_id` 为 "TR-GN-INIT-001、TR-GN-INIT-002、TR-GN-INIT-003、TR-GN-INIT-005、TR-GN-INIT-006、TR-GN-INIT-008"，则 `correspond_fun_id` 为 "TR-GN-INIT-001、TR-GN-INIT-002、TR-GN-INIT-003、TR-GN-INIT-005、TR-GN-INIT-006、TR-GN-INIT-008"。
- `test_step` 是数组；每个元素必须包含 `步骤描述` 和 `预期结果`。可选地，附加以下语义锚点字段：
- `operation_type`：操作类型，取值为 send_command / inject_input / trigger_output / set_input_data / set_memory / verify_telemetry / verify_response / verify / bus_communication / initialization / other
- `channel`：实际操作通道，按需求填写 CANA / CANB / 二级CANA / 二级CANB / SPI；内存写入、中断、人工检查留空。不得将所有功能需求固定映射到 CANA。
- `temporal`：时间描述，如 "第3.0秒"
- `data_checks`：预期结果中的具体检查项列表
- 示例 step 元素：{"步骤描述":"第3.0秒，通过CANA总线发送指令","预期结果":"系统接收到指令。","operation_type":"send_command","channel":"CANA","temporal":"第3.0秒"}

### 通用生成规则

功能分类不改变接口的实际操作模型。下方按当前需求注入的接口模型与 `functional_model_rules` 优先于通用收发、同包恢复及 step_plan；输出流中的软件动作只能写入预期结果，不能变为测试系统的输入步骤。引导加载、初始化等本次无自动化操作的人工需求保留人工步骤，不做关键字翻译。
- 只输出严格 JSON 数组，不要输出解释、标题或代码块标记。
- 仅围绕当前测试需求项相关内容生成，不补充无关场景。
- 先通读整个测试需求项的全部上下文，再按指令/功能类型划分用例：同一指令/功能类型的多种情况，即使分散在多个 TR-ID 对应的描述条目中，也必须聚合到同一个用例中一起测试，不得按 TR-ID 逐条拆分用例。
- `步骤描述`写人工操作，`预期结果`写可观察、可验证结果。
- `步骤描述`和`预期结果`都以中文句号结尾。
- `步骤描述`只描述使用哪个协议/数据格式及数据状态（正确/哪个字段错误），禁止给出协议的具体字节值（如"41H 08H 20H..."）。具体数据由后续步骤生成。
- JSON 必须使用双引号、无末尾逗号、可直接解析。

### TR项组合与覆盖规则（强制遵守）

**前置条件**：若提示中存在 `<cross_requirement_context>`，其上游数据流是触发本需求处理逻辑的前提条件。你需要理解跨需求数据流与当前处理逻辑的因果关系，在用例步骤中体现发送前置数据流的操作。前置数据流通常描述可通过仿真总线发送的输入数据格式。

1. **理解TR描述的逻辑子部分**："处理"字段中的每个TR描述可能包含多个逻辑子部分（如不同的条件分支、不同的处理步骤、不同的判定结果等），你需要理解这些逻辑子部分并识别它们。

2. **自由组合生成用例**：根据测试需要，从众多TR描述的逻辑子部分中合理选择条目来组合成适合生成一个测试用例的依据。可以只选取"TR-001：TR-001描述"的A部分与"TR-003：TR-003描述"的C部分为依据来生成测试用例，选取的依据是这些部分之间存在逻辑关联，适合在同一用例中一起测试，而不是只因为来自同一TR描述才放在一起。

3. **强制覆盖率要求**：所有生成用例的依据必须完整覆盖"处理"字段中所有TR描述的所有逻辑子部分（假设共有N个逻辑子部分，所有用例覆盖的部分的并集必须等于这N个部分，不得遗漏任何一个）。

4. **避免重复**：不同用例之间选取的依据尽量不要重复，除非多个用例确实都依赖同一逻辑子部分。

5. **总线收发类功能需求**（需求描述“通过一级CAN总线收到指令X → 发送/返回Y”形态，如轮询指令/遥控指令/内存读出的接收处理）按接口测试同款模式设计：**每条指令 × 每条接收总线（CANA/CANB）＝ 一个独立用例**（A、B总线的故障可能只出现在一条上，不得合并在同一用例）；用例内按“全部正确 → 错误注入 → 全部正确”交替编排，覆盖需求**及其引用条款**描述的错误分支（如“仲裁场/控制场、TITLE、SUM、W0~W1错误的处理见TR-JK-001~003”——注入仲裁场错误、TITLE错误、SUM错误、W0错误、W1错误等，每个错误后必配一次正确恢复）；非总线收发类的多通道场景（如同时配置多个通道参数）仍在同一用例内拆成多条步骤。

6. **协议格式表是覆盖清单，不是背景材料**：总线接收类功能需求必须读取输入流格式表，区分数据包数量、统计每包帧数，并覆盖表中全部适用校核字段；仲裁场和控制场必须分别测试，禁止合并成一个错误。单帧轮询控制序列按字段/字节逐项覆盖；多帧数据按首帧、中间代表帧、尾帧覆盖适用字段和帧序号错误（2帧仅首帧+尾帧）。每个错误步骤只允许一个字段或一种帧序号错误。

7. **两个多帧辅助数据包**：采用统一多包规则：完整正确包1→包1单字段错误→包2剩余错误逐项发送→完整正确包2；不再重复旧四步组。首/中/尾代表帧适用字段及帧序号错误由两包共同覆盖，正确计数仅在正确包递增，错误计数仅按需求检查。

8. **内存读出指令**：每条总线分为“全字段错误+正确恢复交替”和“地址边界”两个用例。非4字节对齐地址必须直接按错误指令处理，不得对齐后接受。每个地址区间覆盖下边界-1/下边界/下边界+1/中间对齐值/上边界-1/上边界/上边界+1，窄区间重合值去重。

9. **内存数据轮询**：第1步必须于第3.0秒启动以5秒为周期循环发送正确内存读出指令；后续在5.0、10.0、15.0秒…（每次前置指令后2秒）发送正确/单字段错误交替的内存数据轮询控制序列；前置指令不得用初始化内存代替。

10. **有序多包含双辅助数据包**：正确包1→包1单字段错误→正确包2→包2另一单字段错误→…→正确包n。每步一个完整包，真实包数依据协议，正确包1至n必须全部按序发送。所有包共同覆盖字段错误，不要求每包穷举；剩余错误在正确包n之前使用包n逐项补测，允许这部分连续错误；错误已测完则剩余包连续正确发送。最终以完整正确包n收尾，仅需求明确多轮运行时才重复完整序列。

### 生成后自检清单（输出前必须逐条确认）
- [ ] 是否已识别出"处理"字段中所有TR描述的所有逻辑子部分？
- [ ] 每个用例是否合理组合了存在逻辑关联的子部分？
- [ ] 所有逻辑子部分是否已被全部用例完整覆盖（无遗漏）？
- [ ] 不同用例覆盖的子部分是否尽量不重复？
- [ ] 每个用例的 `covered_tr_items` 是否列出了选取依据的所有TR-ID？
- [ ] `correspond_fun_id` 是否从 `normalization_context.requirement_id` 原样照抄（、分隔的多ID格式）？
- [ ] 总线接收类需求是否从格式表识别了包数、帧数并覆盖全部适用字段，而不是只抽样部分错误？
- [ ] 2帧数据是否按首帧+尾帧处理；多包含双辅助数据包是否正确包1至n完整推进、末包正确前补齐剩余错误且计数连续？
- [ ] 内存读出是否将非4字节对齐当作错误并补齐每个区间的边界集？内存数据轮询是否保留3s/5s周期前置及2s偏移时序？

- 输出流说明：{outputFlowContext}
- 测试要求：{constraintContext}
```
