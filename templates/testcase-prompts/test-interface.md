# 测试版接口测试提示词模板

## 适用范围
- 模板 Key：`test-接口测试-STEP-GENERATED`
- 说明：适用于 software / software_variant + 接口测试。

## 业务说明
用于软件接口协议验证场景。 提示词正文已收敛为短结构，业务人员如需优化，优先调整"类型专属规则"和"输入信息"的表达，不要在 `prompt` 代码块中加入大段示例或教学说明。

## 占位符
- `{title}`：测试需求项名称。
- `{requirementContext}`：测试需求项简介。
- `{inputFlowContext}`：输入流说明。
- `{processingContext}`：测试需求项具体涉及的处理逻辑。
- `{outputFlowContext}`：输出流说明。
- `{constraintContext}`：测试要求。
- 若正文中未使用某个占位符，可忽略对应说明。

## 提示词正文
```prompt
### 任务目标
你要为一条接口测试需求项生成测试用例。输入的"处理"字段中包含多个"TR-ID：TR-描述"条目，你需要整体考虑所有子接口测试需求项。用例划分粒度是**具体指令**（数据流定义中逐条列出的指令名），不是指令类别：遥测帧1轮询控制序列、遥测帧2轮询控制序列、内存数据轮询控制序列是三条**不同指令**，即使同为单帧格式也必须各自独立成一个用例（每条指令×每条总线＝一个用例）；"单帧/多帧"等类型概念只用于选择错误覆盖策略，不得作为合并不同指令的依据。

### 输出格式
- 只输出 JSON 数组。
- 每个用例必须包含 `test_case_name`、`test_purpose`、`covered_tr_items`、`correspond_fun_id`、`test_step`。
- `test_case_name` 使用简洁的中文短语描述该用例的测试场景，如"遥测帧1轮询控制序列ID错误丢弃测试"，不要使用"TR-JK-001"等编号作为名称。
- `covered_tr_items` 是一个字符串数组，列出本用例覆盖的具体 TR 子需求项编号（如 ["TR-JK-001", "TR-JK-002"]）。根据输入的"处理"字段中列出的 TR 项确定哪些与本用例相关。
- `correspond_fun_id` 是一个字符串，从 `<normalization_context>` 中的 `requirement_id` 原样照抄（、分隔的多ID格式）。示例：若当前需求的 `requirement_id` 为 "TR-JK-001、TR-JK-002、TR-JK-003、TR-JK-005、TR-JK-006、TR-JK-008"，则 `correspond_fun_id` 为 "TR-JK-001、TR-JK-002、TR-JK-003、TR-JK-005、TR-JK-006、TR-JK-008"。
- `test_step` 是数组；每个元素必须包含 `步骤描述` 和 `预期结果`。**每条步骤必须附加以下语义锚点字段**（不可省略）：
- `operation_type`：操作类型（必填），取值为 send_command / inject_input / trigger_output / set_input_data / set_memory / verify_telemetry / verify_response / verify / bus_communication / initialization / other。根据步骤语义准确选择。
- `channel`：总线通道（必填），取值为 CANA / CANB / 空字符串（非总线操作时填空字符串）。
- `temporal`：时间描述（时序相关步骤必填），如 "第3.0秒"、"第10.8秒"。
- `data_checks`：预期结果中的具体检查项列表（选填），如 ["仲裁场=8DH", "W170为1"]。计数类检查必须写明可观测的绝对值；需求未说明初始值时假定初值为 0（"加1"对应"为1"）。本条不适用于专属分节明示"保留字面文本"的固定句式用例（如硬件狗的"清看门狗最大时间"——该文本不是待解析占位符，禁止用需求中的其他数值填充）。
- 示例 step 元素：{"步骤描述":"第3.0秒，通过CANA总线发送指令","预期结果":"系统接收到指令。","operation_type":"send_command","channel":"CANA","temporal":"第3.0秒"}

### 通用生成规则
- 只输出严格 JSON 数组，不要输出解释、标题或代码块标记。
- 仅围绕当前测试需求项相关内容生成，不补充无关场景。
- 先通读整个测试需求项的全部上下文（输入的"处理"字段可能是逐条 TR-ID 枚举形态），再按**具体指令**划分用例：**同一条指令**的多种情况（不同字段错误、正确/错误交替、不同 TR 描述的校核点），即使分散在多个 TR-ID 对应的描述条目中，也必须聚合到同一个用例中一起测试，不得按 TR-ID 逐条拆分用例。**不同指令（即使格式相同，如同为单帧、或同受一条 TR 约束）必须各自独立成一个用例**——禁止把"遥测帧1~4轮询+内存数据轮询"这类多条指令揉进一个用例后只实测其中一条。
- `步骤描述`写人工操作，`预期结果`写可观察、可验证结果。
- `步骤描述`和`预期结果`都以中文句号结尾。
- JSON 必须使用双引号、无末尾逗号、可直接解析。

### 多TR项组合与覆盖规则（强制遵守）

输入的"处理"字段中包含多个"TR-ID：TR-描述"条目。你需要整体考虑所有子接口测试需求项，提取共性测试点生成用例。

1. **分析阶段**：解析每个子 TR 涉及的指令/数据流类型和异常校核要求，识别出所有异常的校核点（仲裁场错误、控制场错误、帧序号错误、TITLE/SUM 错误、逐字节错误等）。

2. **分组阶段**：按**具体指令**划分（数据流定义逐条：遥测帧1轮询控制序列、遥测帧2轮询控制序列、遥测帧3轮询控制序列、遥测帧4轮询控制序列、内存数据轮询控制序列、10字节遥控指令、15字节遥控指令、上行数据块、72字节上行数据块、内存读出指令、辅助数据包、星务时间广播数据……各是一条独立指令），**每条指令×每条总线=一个独立用例**。"单帧/多帧"类型只用于选择该指令的错误覆盖策略（字段/序号规则），不作为合并依据；格式不同或字节长度不同者进一步拆分。

3. **合并阶段**：**同一条指令**被多个子 TR 描述校核时（如 TR-JK-001/002/003 都校核单帧指令的不同字段），把这些校核点并入**该指令**的同一个用例；不同指令不得因 TR 相同或格式相同而合并。合并时按以下优先级：先覆盖所有字段错误，再覆盖帧序号错误（如适用）。

4. **覆盖检查（生成后必须逐条验证）**：
   - [ ] 所有子 TR 的所有异常校核点是否都已分配到某个用例中？
   - [ ] **用例数 = 指令数 × 总线数**是否成立（每条具体指令、每条总线各有独立用例，没有把多条指令揉进同一个用例）？
   - [ ] 同一条指令被多个子 TR 校核的共性校核是否已合并（而非为每个子 TR 各生成一个重复用例）？
   - [ ] 每个用例的 `covered_tr_items` 是否列出了该用例覆盖的全部子 TR-ID？
   - [ ] `correspond_fun_id` 是否从 `normalization_context.requirement_id` 原样照抄（、分隔的多ID格式）？

5. **双冗余总线**：每条总线各自独立一个用例。如 CANA 和 CANB 各有独立的字段/序号测试用例。

### 有序多包优先规则
- 含双辅助数据包，统一按正确包1→包1单字段错误→正确包2→包2另一单字段错误→…→正确包n编排，优先于通用同包错误后立即恢复规则。每步一个完整包，所有正确包按序发送；错误由各包共同覆盖，不要求每包穷举。剩余错误在正确包n之前使用包n逐项补测；错误已测完则剩余包连续正确发送。最终以完整正确末包收尾，仅需求明确多轮运行时重复完整业务序列。

### 总线接口数据流规则（生成前必须理解）

下面对数据流的处理方式不同于普通功能测试，必须遵守以下规则：

0. **总线层级区分** = 若 `<cross_requirement_context>` 中的 `upstream_flows` 条目带有 `bus_level` 字段（如"一级CAN"/"二级CAN"），引用数据格式时**必须确认 `bus_level` 与当前步骤涉及的总线层级一致**，禁止跨层级引用数据格式。例如：通过一级CAN发送的数据，应从 `bus_level="一级CAN"` 的 `inputFlow` 中查找格式定义，而非 `bus_level="二级CAN"` 的格式。

1. **输出流** = 被测软件内部接收并处理数据之后，通过总线向外部单板**发送**的数据。
   - 输出流由软件内部产生，**不需要设计"发送输出流"的测试步骤**。
   - 但必须在预期结果中验证输出流的数据格式是否符合输出流定义。

2. **输入流** = 外部单板处理完毕之后，通过总线**返回**给被测软件的数据。
   - 仿真测试环境没有真实单板，必须生成测试步骤，**通过总线发送符合输入流数据格式的数据**来模拟单板的应答。
   - 如果协议文档中定义了输入流的数据帧格式（如仲裁场、控制场、帧序号等），模拟步骤必须严格按此格式构造数据。

3. **前置触发条件** = 触发软件产生输出流的前提动作。
   - 如果提示中存在 `<cross_requirement_context>`，其中的上游数据流定义了触发本需求处理逻辑所需的前置输入数据格式。
   - 必须在生成用例时**首先生成步骤发送这些前置数据流**，使软件满足产生输出流的条件。
   - 如果 `<cross_requirement_context>` 中的上游数据流也定义了输入/输出流，同样遵循本规则（输入流需模拟，输出流只需在预期结果中验证）。

4. **步骤编排顺序**：
   准备响应数据步骤（如适用，见规则5）
   → 前置触发步骤（<cross_requirement_context> 中的输入流模拟发送）
   → 验证输出流（在预期结果中验证，非操作步骤）
   → 模拟本需求输入流的应答步骤（发送符合本需求输入流数据格式的数据）

5. **被动触发准备步骤** = 若被测软件是向单机发送请求后被动接收应答（输入流为"请求-响应"模式）：
   - 在触发步骤**之前**，先生成准备步骤——使用被动触发关键字预置响应数据文件
   - 仿真平台检测到软件发出请求后，会自动回复已准备好的数据
   - 编排顺序：准备响应数据 → 前置触发 → 验证输出流+自动应答结果

6. **步骤不写具体协议字节值** = 步骤描述中**禁止**给出协议数据的具体字节值（如"41H 08H 20H..."）。步骤描述只需写明：
   - 使用的协议/数据格式名称（如"符合一级CAN总线10字节遥控指令格式"）
   - 数据状态（"全部字节正确"/"仲裁场字节错误"/"SUM字节错误"等）
   具体字节值由后续数据生成步骤填充。

7. 如果某个数据流格式在当前上下文中找不到定义，不要凭空编造；只使用 `<cross_requirement_context>` 和当前需求中明确给出的数据格式。

### 强制覆盖率检查（生成后必须逐条验证，不可跳过）
- 生成完所有用例后，你必须自检以下清单，每条都通过才能输出：
- [ ] 输入流中列出的每一种指令/数据流（遥测帧1/2/3/4轮询、内存数据轮询、10B遥控指令、15B遥控指令、249B上行数据块、72B上行数据块、内存读出指令、辅助数据包、星务时间广播等）是否都已为 CANA 和 CANB 各生成了一个独立用例？
- [ ] 格式不同或字节长度不同的指令是否已拆分为不同用例？
- [ ] 单帧指令的用例步骤是否按 "正确→仲裁场错→正确→控制场错→正确" 编排？
- [ ] 多帧指令的用例是否覆盖了每一帧的字段错误 + 9类帧序号错误（首帧3类/尾帧3类/中间帧3类）？
- [ ] 若需求提及遥测逐字节校核，是否覆盖了逐字节错误？
- [ ] 若需求提及 LENGTH 校核，多帧指令是否覆盖了 LENGTH 错误？
- [ ] 若需求提及 DLC 校核，是否覆盖了 DLC 小于实际长度场景（首帧/尾帧/中间帧）？
- [ ] 若输入流包含星务时间广播，是否考虑了接收与应答之间、多帧数据之间插入 GPS 整秒对时广播？
- [ ] 同用例中步骤描述和预期结果的详细程度是否前后一致？
- [ ] 每个 `test_step` 元素是否只包含一个字段错误？
- 自检通过后在输出末尾添加一行注释说明：`<!-- 覆盖率检查通过: N条指令×2总线=2N个用例，共M个步骤 -->`
```
