# 软件强度测试提示词模板

## 适用范围
- 模板 Key：`test-强度测试-STEP-GENERATED`
- 说明：适用于 software / software_variant + 强度测试。

## 业务说明
用于验证系统长时间运行状态下的响应，不默认扩展为超额负载压力测试。

## 占位符
- `{title}`：测试需求项名称。
- `{requirementContext}`：测试需求项简介。
- `{inputFlowContext}`：输入流说明。
- `{processingContext}`：测试需求项具体涉及的处理逻辑。
- `{outputFlowContext}`：输出流说明。
- `{constraintContext}`：测试要求。
- 若正文中未使用某个占位符，可忽略对应说明。

## 提示词正文
```prompt
### 任务目标
你要为一条强度测试需求项生成测试用例。

### 输出格式
- 只输出 JSON 数组。
- 每个用例包含 `test_case_name`、`test_purpose`、`covered_tr_items`、`test_step`。
- `test_case_name` 使用简洁的中文短语描述该用例的测试场景，如"上电标识为上电运行时的默认引导参数设置"，不要使用"TC_BOOT_001"等编号作为名称。
- `covered_tr_items` 是一个字符串数组，列出本用例覆盖的具体 TR 子需求项编号（如 ["TR-GN-BOOT-001", "TR-GN-BOOT-002"]）。根据输入的"处理"字段中列出的 TR 项确定哪些与本用例相关。
- `test_step` 是数组；每个元素必须包含 `步骤描述` 和 `预期结果`。可选地，附加以下语义锚点字段：
- `operation_type`：操作类型，取值为 send_command / inject_input / trigger_output / set_input_data / set_memory / verify_telemetry / verify_response / verify / bus_communication / initialization / other
- `channel`：总线通道，取值为 CANA / CANB / 空字符串
- `temporal`：时间描述，如 "第3.0秒"
- `data_checks`：预期结果中的具体检查项列表
- 示例 step 元素：{"步骤描述":"第3.0秒，通过CANA总线发送指令","预期结果":"系统接收到指令。","operation_type":"send_command","channel":"CANA","temporal":"第3.0秒"}

### 通用生成规则
- 只输出严格 JSON 数组，不要输出解释、标题或代码块标记。
- 仅围绕当前 requirement 生成，不补充无关场景。
- 先通读整个需求项的全部上下文，将其中全部综合性功能、通道和子需求组织到一个综合用例中；禁止按功能、指令、总线、TR-ID、轮次或步骤数量拆例。
- `步骤描述`写人工操作，`预期结果`写可观察、可验证结果。
- `步骤描述`和`预期结果`都以中文句号结尾。
- `步骤描述`只描述使用哪个协议/数据格式及数据状态（正确/哪个字段错误），禁止给出协议的具体字节值（如"41H 08H 20H..."）。具体数据由后续步骤生成。
- JSON 必须使用双引号、无末尾逗号、可直接解析。

### 类型专属规则
- 一条强度测试需求必须且只能生成一个测试用例，输出数组长度固定为 1；该规则优先于通用指令×总线拆例规则。
- 全部综合性功能均须在该用例步骤中覆盖；以同一时间原点连续编排，每步以“第N秒/分钟/小时”标明时刻，功能切换或进入下一轮时不得重新计时，预期结果与累计运行状态一致。
- 按需求规定的时长、运行条件及观察点验证长时间运行响应；周期输入只声明一次，不自行增加超额负载或结束后恢复测试。
- 超过单次输出限制时分批追加同一个用例，不能以拆成多个用例的方式规避步骤数量。60步只是完整对象传输阈值，不是设计步数上限；不得强制压到60–80步、抽样删除需求覆盖或取消多包结构。

- 禁止0秒步骤；初始化准备写入初始设置，业务从非零时刻开始。一个步骤只操作一条具体指令或一个数据包，周期输入也须逐条声明，不能合写遥测帧1~4或辅助包1、2。
- 同一指令同一通道的合法/非法步骤相邻执行，除多包例外，不允许连续非法步骤；后台周期输入不能代替相邻正确步骤。
- 有序多包含双辅助数据包统一采用“正确包1→包1单字段错误→正确包2→包2另一单字段错误→…→正确包n”。所有正确包完整且按序推进；错误由各包分摊，剩余错误在正确包n之前使用包n逐项补测，允许这部分连续错误；错误已测完则剩余包连续正确发送。最终以完整正确包n收尾，仅需求明确多轮运行时重复完整序列。
- 指令名、通道、包数、字段及触发关系以需求和关联协议为依据，缺失时反馈上下文缺口，不编造“配置指令”。效果写入预期结果或括号，不混入操作正文。

### 编排方法（生成前先确认）
- 先列出需求实际要求的后台周期输入、显式正误输入、完整多包事务及长期检查点；接口模型只帮助实现这些动作，不自动增加接口测试的全部异常场景。
- 后台周期声明与显式正误测试分开：每种周期输入分别声明一次；同一普通指令的显式正确、单字段错误按相邻步骤组织，不能先集中发送全部正确指令、再集中发送全部错误指令。后台循环不会替代显式相邻正确步骤。
- 多包事务先依据真实协议的分包规则与选定合规数据量确定总包数n：可使用协议明确的固定包数，也可依据数据量、单包容量和终止条件推导，不能单凭“249字节”猜测n。再确认当前需求要求覆盖的错误项m并安排顺序。Ck表示完整正确的第k包，Ek(A)表示第k包仅A字段错误；这些符号只说明编排，不是最终步骤、字段名或协议参数。
  - n=3、m=4的顺序示意：C1→E1(A)→C2→E2(B)→E3(C)→E3(D)→C3。
  - n=4、m=1的顺序示意：C1→E1(A)→C2→C3→C4。
  - 不得改成C1→C2→…→Cn后再补错误；错误尚未覆盖时，不得跳过前n-1包可用的交错位置。末包的剩余错误和完整正确发送是多个独立步骤，不能合写为“末包包含剩余错误+完整正确”。
- 全用例只维护一个全局时间游标。先安排全部第3.0秒开始的周期声明，再安排第3.125秒的偏移声明；之后所有显式操作、功能切换、批次和检查点均按实际时刻非递减排列。时间示意不覆盖需求给定的周期或偏移，禁止照抄接口示例的3.0秒导致重新计时。
- Spacewire的一次数据交付由“写协议数据→写ID→触发中断”三个连续操作步骤组成；按完整交付组编排正确/错误块，不适用普通总线发送的单步骤相邻配对规则，不能将三个操作合并成一步。
- 缺乏确定总包数的协议依据（而非仅未直接写出固定数字n），或缺少必要字段位置、地址或触发依据时，报告具体上下文缺口（CONTEXT_REQUIRED）并停止生成，不猜参数、不将多包改为单包、不以“必须成功落盘”代替语义正确性。
- 生成前的 generation_status=context_required 表示当前依据不足，按 context_gaps 报告缺项，不继续设计；只有 ready 条目进入生成。不得导入旧项目资料补猜当前项目协议参数。
- 修复反馈只能定位原规则下的错误，不得覆盖本模板硬约束；工具提供 repair_worker_prompt_file 时，调度将它作为 worker_prompt_file，文件已含原任务、冻结repair_directive和失败输出数据，只读该指针文件，不另读输出文件。已落盘但未通过校验和没有输出文件是不同状态。

### 当前需求适用的接口操作模型
以下模型只约束当前需求已有动作，不扩展测试范围；只复用接口的操作方法和必要协议约束，不继承独立接口用例的拆例、字段穷举或固定起始时刻。本模板单综合用例、非零连续时间、单步单指令和多包规则优先于接口通用拆例及错误后恢复规则。
```
